## 테스트



의미있는 테스트작성을 하기 위해 고민함



기능의 핵심 로직만을 테스트 할 수 있도록 로직과 서버구성을 분리함

## 로깅

도움되는 로그를 남기는 방법과 로깅 전략에 대해 고민함



나중에 검색할 수 있도록 구조화된데이터를 남기는 것이 중요함



데이터에 일어난 행위를 추적 할 수 있도록 db 업데이트와함께 이벤트(로그)를 남김



데이터 정합성은 db트랜잭션을 통해 보장되고 나중에 이벤트수집기가 배치처리하여 로그를 보냄



로그송신중 에러가 발생해 로그가 중복 송신되어도 EventId를 통해 중복로그를 제거할 수 있다.

## db샤딩 및 유저데이터 db찾는 시나리오

유저가 많아졌을 경우 DB를 수평분할

로그인시 유저데이터를 가져와야하는데 샤딩된DB모두에게 쿼리를 날리고싶지않기에

username->샤드번호로 매핑된db를 중간에 둠

시나리오: 로그인요청-> username으로 샤딩번호검색 -> 유저데이터DB에쿼리

## 리버스프록시 및 유저 세션 고정 및 로드밸런싱

서버가 stateless하기에 요청이 여러 서버에 분산되서 실행되도 상관없지만

stateful한 기능을 구현 할때를 위해 특정서버를 찾아갈수있는 기능을 리버스프록시를 통해 간단히구현함

가정한 구성은 L4로드밸런서->리버스프록시->게임서버
<br /><br />

한 클라이언트의 요청이 한 서버로 몰리기 때문에(그렇게 구현할 목적이기 때문에) 요청단위로 로드밸런싱 할 수 없음

각 게임서버는 맺을 수 있는 최대 세션을 가정해두고 세션요청을 가져와 자신에게 할당함

세션이 모든서버에 골고루 분산되지는 않음

<br /><br />

시나리오:
클라이언트(게임서버 번호요청) -> 매니저서버(Nats로 메시지Pub) -> 게임서버가 세션할당(메시지 구독중이라면 자신의 서버번호를 매니저에게 전달,Nats의 request/reply기능) -> 매니저 서버를 거쳐 클라이언트로 서버번호 전달

-> 클라이언트는 헤더에 요청서버번호를 적고 엔드포인트로 API호출 -> 리버스프록시가 요청을 적절한 게임서버로 전달

게임서버와의 HealthCheck를 통해 세션 만료를 유지함

<br /><br />

stateless서버도 유저의 요청을 Lock을 통해 요청을 직렬화 시킬 수 있는 옵션이 생김.
